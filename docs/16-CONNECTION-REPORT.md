# 16 連線穩定度驗證報告（2026-11-22，分支 review/connection；**只驗證，不含程式修改**）

> **白話摘要（給不熟技術的人）**
> 1. 手機「網路換手」（Wi‑Fi↔4G、訊號忽好忽壞）時，舊連線會變成「看起來還連著、其實已經斷了」。目前雙方都**發現不了**：我們實測 90 秒，手機沒顯示斷線、其他人也看不到他離線，這段時間按的東西直接不見。這最可能就是「很容易斷線」的主因。
> 2. 伺服器更新或被雲端重啟時，**所有房間會一起消失**；實測每個人的畫面停在遊戲中、倒數照跑，只跳出一行 4 秒就消失的提示，按什麼都沒用，也不會自動回首頁。
> 3. iPhone 鎖螢幕或切到別的 App，連線幾乎一定會被系統關掉（公開資料）；回來後程式會立刻重連（實測 0.03 秒），但已知 iOS 有時新連線會「一直連線中」卡住，目前程式**沒有逾時**可以跳出來。
> 4. 一般斷線（網路直接中斷）處理得不錯：0.02 秒內顯示「連線中斷」、網路恢復後幾秒內自動回到原本角色和畫面，斷線時按的東西會補送。
> 5. 建議先做三件小工程：心跳逾時偵測、連線逾時與回前景強制重連、房間不見時清楚帶大家回首頁；接著再做「房間存檔」讓伺服器更新不會打斷遊戲。以上全部**未用真手機測試**。

## 1. 範圍與方法

- 本機實驗：`npx wrangler dev`（本機模擬 Cloudflare Worker＋Durable Object）＋ Playwright Chromium 開 3 支模擬手機（甲＝房主、乙、丙）。丙的連線經過自寫的 TCP 代理，可以切成：
  - `kill`：直接切斷，並在一段時間內拒絕新連線（＝網路完全斷掉、iOS 背景關閉連線）。
  - `blackhole`：不關閉連線，但兩個方向的資料都丟掉（＝網路換手後舊連線變成「半開」）。
  - `refuse`：拒絕新連線。
- 實驗腳本放在 scratchpad（不 commit），可依本文描述重寫：代理約 25 行、每個實驗一段 Playwright。
- `npm test` 基準：126／126 通過（未改程式）。
- **無法在此環境模擬**：iOS Safari、Android Chrome 真機的背景行為、真實行動網路。這些以官方文件／WebKit bug 為依據，標「推論」。

## 2. 現況程式重點（與連線有關）

| 項目 | 現況 | 位置 |
|---|---|---|
| 重連 | `onclose` 後指數退避 300ms×2ⁿ，最多 5 秒，無限重試 | `public/net.js` `scheduleRetry` |
| 回前景 | `visibilitychange` 變 visible 且 socket 是 **CLOSED** 才立刻重連；CONNECTING／CLOSING／「假 OPEN」都不處理 | `public/net.js` |
| 心跳 | 每 20 秒送 `ping`，伺服器回 `pong`；**手機不檢查有沒有收到 pong**，伺服器也不檢查多久沒收到 | `net.js`、`hub.ts` |
| 連線逾時 | 沒有；卡在 CONNECTING 只能等瀏覽器自己放棄 | — |
| 遊戲操作 `act` | 有唯一 id，未 ack 前重連會重送、伺服器去重 | `net.js`、`room.ts seenActs` |
| 其他訊息（投票、背包偏好、開始、下一局…） | 斷線時排隊，**但 socket「假 OPEN」時直接送進黑洞、不重送** | `net.js send()` |
| resume 失敗 | 只有「還沒有畫面」時才清 session 回首頁；遊戲中只跳一則 toast | `app.js onError` |
| 伺服器 | 所有房間在同一個 Durable Object（`global`）記憶體；標準 `accept()`（非 Hibernation）；`setInterval` 250ms tick；沒用 storage 存房間 | `src/worker/index.ts` |
| 斷線規則 | 斷線＝`connected=false`：房主移交、操作轉交、表決不算離線者（已有單元測試 F18、表決測試） | `room.ts` |

## 3. 逐項驗證結果

### 3.1 半開連線（Wi‑Fi↔4G 換手、訊號不穩）— **重現**，嚴重度：高

實驗 X2（大廳中，丙的連線 `blackhole` 90 秒）：

| 量測 | 結果 |
|---|---|
| 丙畫面出現「連線中斷」橫幅 | 90 秒內**從未出現**（`ws.readyState` 一直是 1＝OPEN） |
| 房主甲看到丙「離線」 | 90 秒內**從未出現** |
| 丙在這段期間點「油燈」 | **遺失**：恢復後甲看到的丙仍是「外衣」，丙自己畫面也是「外衣」（伺服器權威，按了沒反應） |

原因：手機每 20 秒送 ping，但不管有沒有 pong；伺服器只靠 TCP close 事件判斷離線。真實網路換手時，舊 TCP 連線要等作業系統重傳逾時（通常數分鐘）才會被宣告死亡（推論，依 TCP 行為）。

連帶影響（由程式推得）：
- 伺服器認為他還在線 → 他的職能**不會轉交**別人；如果他是補船或衝向海灘的負責人，全隊會卡住直到 TCP 逾時。
- 表決把他算成「在線但沒回應」→ 等滿 10 秒才算同意（規則上能過，但每次都要等 10 秒）。
- `act` 會留在待送清單，但因為連線一直「看起來 OPEN」，**不會觸發重連**，就不會補送。
- 投票、背包偏好、開始、下一局等一般訊息**直接遺失**。

### 3.2 伺服器重啟／部署／Durable Object 被回收 — **重現**，嚴重度：高

實驗 X5（開局後重啟 wrangler dev，模擬 Worker 部署或 DO 重置）：

| 量測（重啟完成後 15 秒） | 3 支手機都一樣 |
|---|---|
| 連線橫幅 | 沒有（已重新連上新的伺服器） |
| 提示 | toast「房間已經不存在，請重新加入」（3.8 秒後消失） |
| 畫面 | **停在遊戲中**，倒數繼續跑（截圖顯示 07:40）、所有按鈕仍在 |
| localStorage 的 session | 仍在（沒有清） |
| 按畫面上的按鈕 | 只再看到同一則錯誤 |
| 45 秒後是否自動回首頁 | **否** |

雲端上何時會發生（官方文件）：
- 部署新版：Durable Object 預設最多延後 300 秒等待休眠，用標準 WebSocket API（本專案就是）**無法休眠**，所以 300 秒內一定被重置，「記憶體狀態遺失、WebSocket 中斷」。（[Durable Objects WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)、[2026-10-30 changelog](https://developers.cloudflare.com/changelog/post/2026-10-30-durable-objects-deferred-code-updates/)）
- 不部署也會：「Cloudflare updates to the Workers runtime」、「runtime decisions on where to host objects」都會重啟物件。（[Durable Object Lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)）Cloudflare 更新全球網路時也會重啟伺服器、終止 WebSocket。（[Cloudflare WebSockets](https://developers.cloudflare.com/network/websockets/)）
- 因為**所有房間在同一個物件**，一次重啟＝全部房間同時消失（ADR-0005 已預期）。
- 推論：開發期間一天部署多次（含 preview 以外的正式版），正好撞上有人在玩的機率不低；最近幾次「很多人同時斷」很可能屬於這一類。

### 3.3 鎖螢幕、切 App、瀏覽器進背景 — 部分**重現**＋**推論**，嚴重度：高

本機能測的：
- X1 硬斷線：丙 21 毫秒內顯示「連線中斷，正在重新連線…」，甲 3 毫秒內看到丙離線；10 秒內嘗試重連 6 次；網路恢復後 **4.3 秒**重連完成（等退避到期）；斷線期間點的「外衣」**有補送**成功。
- X4 退避已拉到 5 秒時觸發 `visibilitychange`：**25 毫秒**重連完成（回前景捷徑有效）。
- X7 遊戲中斷線 8 秒後恢復：1.4 秒連上，職能（船長、瞭望）、按鈕（lock 等）、階段都和斷線前一致；倒數正確（07:59→07:49）。
- X3 Chromium 頁面凍結（CDP `Page.setWebLifecycleState frozen`）60 秒：連線沒斷、伺服器沒判離線；解凍後 1 秒內補上期間的變化（看到甲改成油燈）。

不能本機測、依公開資料推論：
- iPhone 鎖螢幕或把 Safari 縮到背景時，WebSocket 會被立即關閉（close 1006）。（WebKit [bug 247943](https://bugs.webkit.org/show_bug.cgi?id=247943)、[Apple 開發者論壇](https://developer.apple.com/forums/thread/716118)）→ 回來時會走 X1／X4 的路徑，通常能恢復。
- **iOS 26.3 回前景後新建的 WebSocket 一直停在 CONNECTING、沒有任何事件**，回報者說只有重新整理頁面能解。（WebKit [bug 308073](https://bugs.webkit.org/show_bug.cgi?id=308073)）目前 `net.js` 沒有連線逾時、回前景只處理 CLOSED → **會卡在「連線中…」直到使用者自己重新整理**。
  - 本機近似實驗 X6（TCP 接受但升級永遠沒回應）：Chromium 自己約每 15 秒放棄一次再重試（60 秒內 4 次），期間一直顯示「連線中…」；觸發回前景**沒有作用**（因為是 CONNECTING）；網路恢復後要等目前那次卡住的嘗試逾時，**7.3 秒**才連上。iOS 若沒有這個內建逾時，就會一直卡著（推論）。
- Android Chrome：背景分頁的計時器被節流（每秒最多 1 次，背景 5 分鐘後每分鐘 1 次），有 WebSocket 的頁面不會因逾時被關，但仍受節流（[Chrome 57 背景分頁](https://developer.chrome.com/blog/background_tabs)、[Chrome 88 計時器節流](https://developer.chrome.com/blog/timer-throttling-in-chrome-88.md.txt)）。20 秒心跳在背景可能變成每 60 秒 1 次，仍在 Cloudflare 閒置上限內（推論）。省電模式下 Chrome 可能凍結分頁（[freezing on energy saver](https://developer.chrome.com/blog/freezing-on-energy-saver)）。

### 3.4 閒置沒有流量被關閉 — **部分排除**，嚴重度：低

實驗：從此環境直接連正式版 `/ws`，一條完全不送資料、一條每 20 秒送 ping（同正式版前端）。

| 連線 | 結果 |
|---|---|
| 完全不送資料 | **300.6 秒**被關閉（code 1006） |
| 每 20 秒 ping | **20 分鐘**後仍連著（測試上限），收到 pong 56 次以上 |

注意：此環境出站要經過代理，300 秒可能是代理或 Cloudflare 造成，**無法區分**。Cloudflare 文件只說「沒資料會關閉、請做心跳」，沒寫秒數（[Cloudflare WebSockets](https://developers.cloudflare.com/network/websockets/)）。結論：現有 20 秒心跳足以防閒置關閉；唯一風險是 iOS 背景時 JS 停止、不送心跳——但那時系統本來就會關連線（3.3）。

### 3.5 前端重連期間的 UI — **重現**，嚴重度：中

- 好的：真的斷線時橫幅很快出現（21ms）、重連後畫面正確（X1、X7）。
- 問題：
  1. 半開時完全沒提示（3.1）——玩家只覺得「按了沒反應」。
  2. 卡在 CONNECTING 時永遠顯示「連線中…」，沒有秒數、沒有「重新整理」按鈕（X6）。
  3. 房間消失時只有 3.8 秒 toast，畫面像沒事一樣（3.2）。
  4. 斷線時按鈕仍可按；`act` 會補送，但畫面沒有「已記下、連上後送出」的提示；伺服器權威的東西（背包、投票）在連回前不會變，看起來像沒按到。

### 3.6 伺服器端規則（斷線轉交、表決、房主）— **大致排除**，嚴重度：中（取決於 3.1）

- 已有測試：`test/server.test.ts` F18（斷線重連回原職能、房主移交、離線操作轉交、重送不重複）、「表決：沒回應的時間到算同意；離線的人不算進表決」皆通過。
- 程式審查：提案人離線→表決取消（`proposalValid`）；房主離線→優先移交給本局隊員；這些規則合理、不違反 DECISIONS 18。
- 但它們**全靠「伺服器知道誰離線」**，而 3.1 顯示半開時伺服器不知道。所以修好 3.1 這些規則才會真的發揮作用。
- 小發現：Worker 版 `close` 與 `error` 都呼叫 `hub.close`，會跑兩次（無害）。重連時舊連線若還沒關，新舊兩條都會收廣播（無害，浪費流量）。

### 3.7 其他

- Safari bfcache：`net.js` 沒處理 `pageshow`（`persisted`）／`pagehide`。新版 Chrome 進 bfcache 時會斷開 WebSocket（[blink-dev PSA](https://groups.google.com/a/chromium.org/g/blink-dev/c/52nlr8z3Png)），Safari 的行為未找到官方說明；回來時若 close 事件沒觸發或觸發時頁面被凍結，可能不會重連（推論，未重現）。
- 沒有監聽 `online` 事件：網路恢復時仍要等退避（最多 5 秒；X1 實測 4.3 秒）。
- 單一 DO 的延遲：所有房間的物件放在第一個請求附近的機房；台灣使用者通常會在亞洲，影響小（推論）。

## 5. 加強方案（只寫計畫，未實作；建議順序即編號）

### P1 心跳逾時偵測（雙向）— 成本：小
- 做法：手機記錄「最後收到任何訊息的時間」；每 10 秒 ping，超過 25 秒沒收到任何東西就 `ws.close()` 並立刻重連（不等退避）。伺服器每個 conn 記 `lastSeen`，tick 時超過 45 秒沒收到就當作斷線（呼叫 `hub.close`、關掉 socket）。
- 解決：#1、#5（重連後 act 補送）、#6（職能轉交開始生效）。
- 風險：背景節流讓 ping 晚送 → 伺服器誤判離線；45 秒寬限足以涵蓋 Chrome 背景每分鐘 1 次以外的情況（背景 5 分鐘以上本來就不在玩）。誤判的代價只是一次重連。
- 驗收：自動—重做 X2，丙 30 秒內出現橫幅並自動恢復、甲 50 秒內看到丙離線、期間點的東西最後有生效。真手機—「遊戲中把一支手機從 Wi‑Fi 切到行動網路，30 秒內該手機回到原角色，其他人看到他回來」。

### P2 連線逾時＋回前景／恢復網路時強制重建 — 成本：小
- 做法：建立連線 6 秒內沒 open 就丟掉重來；`visibilitychange` 變 visible、`online`、`pageshow`（persisted）、`resume` 事件時：若不是 OPEN，或 OPEN 但 > 15 秒沒收到訊息，就直接關掉重建並把退避歸零。連續 3 次逾時，橫幅加「重新整理」按鈕（針對 WebKit bug 308073）。
- 解決：#3、#8。
- 風險：低；要避免同時兩條連線（用一個 generation 編號，舊的事件忽略）。
- 驗收：自動—重做 X6，網路恢復後 ≤ 7 秒連上，觸發 visibilitychange 時 ≤ 1 秒。真手機—「遊戲中 iPhone 鎖螢幕 30 秒再打開，5 秒內回到原畫面；Android 切到 LINE 1 分鐘再切回來，同樣」。

### P3 房間不見時清楚收尾 — 成本：小
- 做法：伺服器 resume 失敗回帶代碼的錯誤（例如 `ROOM_GONE`）；手機不論是否有畫面，都清 session、停在一個說明頁：「伺服器剛更新，這一局中斷了（不是你的問題）。請房主重新開房，大家掃新的 QR Code。」並附「回首頁」按鈕。
- 解決：#2 的體驗（房間仍會消失，但大家知道怎麼辦）。
- 風險：低。
- 驗收：自動—重做 X5，3 支手機 5 秒內都顯示說明頁、按鈕回首頁可開新房。真手機—（需要工程人員重新部署一次）「玩到一半時請工程人員部署，所有人看到說明頁並能在 1 分鐘內重開新局」。

### P4 斷線狀態清楚顯示 — 成本：小～中
- 做法：橫幅顯示斷線秒數；超過 10 秒顯示「網路不穩，試著切換 Wi‑Fi／行動網路」，超過 20 秒顯示「重新整理」按鈕；斷線時按的操作在按鈕上標「等待送出」；遊戲畫面上（不只大廳）標示哪位隊友離線。
- 解決：#4。
- 風險：畫面更擠（小螢幕 320px 要檢查不橫向捲動）。不違反「不是自己能操作的按鈕不顯示」。
- 驗收：自動—e2e 斷線截圖、320px 無橫向捲動。真手機—「開飛航模式 25 秒，看得懂畫面上的提示並在關閉飛航後自己回到遊戲」。

### P5 所有會改變狀態的訊息都加 id＋ack 重送 — 成本：小
- 做法：`vote`、`pref`、`start`、`next`、`thank`、`submitScore` 比照 `act`：帶唯一 id，伺服器去重並回 ack；未 ack 的在重連後重送。
- 解決：#5。
- 風險：`submitScore` 已有「同一局只登記一次」保護；其餘多送一次也無害，但要確認去重。
- 驗收：自動—單元測試重送同一 id 不重複；重做 X2 後投票／背包有生效。

### P6 房間狀態存進 Durable Object storage，並改用 Hibernation API — 成本：中～大
- 做法：每次房間狀態改變後（節流約 1 秒）把房間序列化存進該物件的 SQLite（已啟用，排行榜在用）；constructor 讀回所有房間。WebSocket 改用 `state.acceptWebSocket()`＋`serializeAttachment` 存 roomCode／playerId；250ms `setInterval` 改成 alarm 或在訊息時推進（setInterval 會阻止休眠）。
- 解決：#2 本身——部署或回收後玩家重連就能 resume 回原局；配合 Hibernation，部署時連線可能根本不斷（官方：休眠後採用新程式碼不會斷 Hibernation WebSocket）。
- 風險：中；房間要能完整序列化（Map、亂數狀態、計時以伺服器時間存）；倒數在重啟期間仍要正確；新舊版本資料格式相容。
- 驗收：自動—重做 X5，重啟後 3 支手機自動回到同一局同一階段、倒數連續。真手機—同 P3 的部署測試，但大家應該**繼續原本那局**。

### P7 部署時機保護 — 成本：小（流程）
- 做法：在 P6 完成前，`wrangler.toml` 可以設 `code_update_strategy`（`deferred`，`max_delay` 拉長，例如 3600 秒）讓進行中的物件延後換版；並約定「有人在玩時不部署正式版」，用 preview 驗證。
- 解決：降低 #2 頻率（不能解決 Cloudflare 自己的重啟）。
- 風險：延後期間新舊版本並存，協定要前後相容（官方 Known Issues）。
- 驗收：部署後 5 分鐘內進行中的房間不斷線（自動：無法本機模擬，需在 preview 實測）。

### P8 每房一個 Durable Object — 成本：大（暫不建議）
- 做法：房號對應各自的物件；建立房間先拿房號再連線。
- 解決：一次重啟只影響一房；擴充性。
- 風險：前端與重連流程要改（ADR-0005 已評估）。P6 做完後全滅的影響已大幅降低，量不大時不值得。
- 驗收：多房壓力測試。

**建議實作順序：P1 → P2 → P3 → P5 → P4 → P6 → P7（P6 之前先用）→ P8（暫緩）。** P1–P3 可一起做，預估一個工作階段；做完先請使用者用真手機跑下面的「5 分鐘連線測試」。

### 給使用者的 5 分鐘真手機連線測試（每次改版後）
1. 3 支以上手機（至少 1 支 iPhone、1 支 Android）開房、開局。
2. iPhone 鎖螢幕 30 秒再打開 → 記錄幾秒回到原畫面。
3. Android 切到別的 App 1 分鐘再回來 → 同上。
4. 一支手機從 Wi‑Fi 切到行動網路 → 記錄他自己和別人各幾秒發現、幾秒恢復。
5. 一支手機開飛航模式 20 秒，期間按一個自己的按鈕，關飛航後看那個動作有沒有生效。
6. 把結果記到 docs/06-TEST_PLAN.md（目前全部：**未測試**）。

## 6. 需要使用者決定的問題（最多 2 題）

1. **伺服器偵測到「一半以上的人同時斷線」時，8 分鐘倒數要不要暫停，等大家連回來再繼續？**（例如伺服器重啟、場地 Wi‑Fi 掛掉）
   建議答案：**要**。（一個字：要／不要）理由：這不是玩家的決策失誤，不該因此輸掉；個別一人斷線則不暫停，照現有的操作轉交規則。
2. **是否同意花中等工程量做 P6「房間存檔」，讓伺服器更新後大家能接回同一局？**（不做的話只做 P3：清楚告知並重開新局）
   建議答案：**做**。（一個字：做／不做）理由：雲端會自行重啟，部署也無法完全避開，只靠告知仍會打斷正在進行的破冰。
