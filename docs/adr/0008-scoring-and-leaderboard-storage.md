# 計分由伺服器算、排行榜存原始資料與公式版本、Cloudflare 用 DO SQLite

Status: accepted（2026-11-16 使用者核准計分與團隊排行榜規格，DECISIONS 17；儲存與公式細節由 AI 決定，未經真人試玩）

## 背景
使用者要每局依團隊表現計分（滿分 1000）、一個永不重置的總榜（前 10 名，同隊名只留最高分），而且手機不能偽造分數。這取代了 AGENTS.md 舊的「不提前做排行榜」限制。公式一定會因試玩資料而改，所以不能把「算好的分數」當唯一的真相。

## 決定
1. **伺服器權威**：分數只由 `src/engine/score.ts` 從房間的規則狀態（`GameState`）取出原始資料再算。`submitScore` 只帶隊名，分數、人數、星數都不從手機來；伺服器檢查房主、這局的隊員、已結算、非練習房、這局未登記、隊名合法。
2. **存原始資料＋公式版本**：每筆登記存 `ScoreRaw`（星數、補船秒數與限時、畫面協助等級、記號格數、是否首局、選錯次數、完成時間、抽到的卡與見聞、是否捲走、解數與難度分、人數）加 `formula`（現為 `v1-trial`）。分數是衍生值，改公式時用原始資料重算，**不清榜**。
3. **每次登記都存**，排行榜顯示時才「每隊取最高、同分取較早」。理由：保留完整資料供重算與分析；用 `roundId`（UNIQUE）防止同一局重複登記。
4. **難度表單一來源**：由 `tools/verify_seeds.py` 計算並產生 `src/engine/difficulty.ts`，引擎只讀不算；golden 測試比對（延續 ADR-0002）。
5. **人數校正係數表**先全 1.0，留好 `PLAYER_FACTOR`，改表必須同時換公式版本。
6. **儲存介面與平台無關**（`LeaderboardStore`，同步介面）：
   - Node 版：預設 `MemoryStore`（只在記憶體）；設 `LEADERBOARD_FILE` 才寫 JSON（暫存檔＋改名）。
   - Cloudflare 版：`SqlStore` 存在既有 `GameHub` Durable Object 的 SQLite（`new_sqlite_classes`，`storage.sql` 為同步 API）。重開、回收、重新部署後仍在。
7. **練習房**（`/solo.html`）由建立房間時帶 `practice: true`；分數照算照顯示、伺服器拒絕登記。同一台電腦開多個一般分頁假裝多人無法辨識，接受此限制並寫進文件。

## Considered Options
- **Workers KV**：最終一致、寫入後各地讀到新值可能延遲，且沒有交易；要做「同隊名取最高」「roundId 唯一」只能自己讀改寫，有競爭風險。不選。
- **D1**：關聯式、可跨 Worker 查詢，但要多建一個資源、綁定與遷移，而且這個專案已經只有一個 Durable Object，所有房間與排行榜寫入都經過它。對這個量（每場幾筆）沒有好處。若將來要多個 Worker 或管理後台才考慮。
- **DO 的 SQLite（採用）**：不用新資源；同一個物件單執行緒，登記不會競爭；`UNIQUE(round_id)`＋視窗函式即可做每隊最高；也和 ADR-0005「單一 Durable Object」一致。代價：排行榜與房間綁在同一個物件，物件大量負載時會互相影響；資料只能經這個物件讀寫，之後要匯出得自己寫 API。
- **只存算好的分數**：簡單，但公式一改榜就不可信或得清榜，與使用者「改公式可重算不必清榜」衝突。不選。
- **Node 版強制寫檔**：區域網路原型多半一次性使用，預設記憶體即可；要保存才設 `LEADERBOARD_FILE`。

## 後果
- 排行榜紀錄有 `hidden`：管理者可用 `setHidden` 隱藏不雅或灌榜的紀錄（不刪資料、不重置榜），目前沒有對外端點。
- 要新增計分欄位時須改 `ScoreRaw` 並升公式版本；舊資料缺的欄位要有預設值。
- 難度表改變（新增故事卡）要重跑 `npm run golden`；舊紀錄已存解數與難度分，可選擇沿用或重查。
- 重算的遷移程式尚未寫；第一次改公式時才做（`LeaderboardStore.all()` 已備好）。
- 隊名冒用、同機多分頁無法防，只靠基本不雅字詞過濾與文件說明（docs/13 第 5 節）。
